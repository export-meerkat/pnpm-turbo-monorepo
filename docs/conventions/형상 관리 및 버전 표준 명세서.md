# 형상 관리 및 버전 표준 명세서

## 1. 개요 (Overview)

### 1.1 목적

본 가이드는 기업의 소프트웨어 개발 및 시스템 운영 전반에 적용할 형상 관리 및 버전 통제 표준을 정의합니다. 이를 통해 소스코드와 산출물의 자산 가치를 보호하고 개발 생산성을 극대화합니다.

### 1.2 범위

- 애플리케이션 소스코드 및 라이브러리
- 인프라 설정 스크립트 (IaC: Infrastructure as Code)
- 프로젝트 기술 문서 및 API 명세서
- 데이터베이스 DDL/DML 스키마 스크립트

### 1.3 기대효과

- 이력 추적성(Traceability) 확보를 통한 장애 대응 시간 단축
- 표준화된 배포 프로세스를 통한 상용 환경 배포 안정성 제고
- 무분별한 코드 수정을 방지하여 소프트웨어 품질 향상

---

## 2. 형상 관리 조직 및 역할 (Roles & Responsibilities)

효율적인 형상 관리를 위해 조직 내 역할을 다음과 같이 정의하고 권한을 분리합니다.

- **형상 관리자 (Configuration Manager)**
  - 형상 관리 표준 프로세스 수립 및 주기적 감사 수행
  - 리포지토리(Repository) 생성 및 역할 기반 접근 권한(RBAC) 통제
- **배포 관리자 (Release Manager)**
  - 스테이징 및 상용(Production) 환경 배포 승인 및 실행
  - 배포 실패 시 롤백(Rollback) 의사결정 및 수행
- **개발자 (Developer)**
  - 담당 기능 생성을 위한 브랜치 격리 및 코드 작성
  - 작업 완료 후 코드 검토를 위한 Pull Request(PR) 발송
- **검토자 (Reviewer)**
  - 발송된 PR에 대한 소스코드 품질 및 아키텍처 준수 여부 검증
  - 변경 사항의 영향도를 평가하여 Merge 승인 또는 반려

## 3. 버전 관리 및 식별 규칙 (Versioning & Identification)

### 3.1 소프트웨어 및 문서 버전 규칙

- **소프트웨어 버전**: Semantic Versioning 2.0.0 표준(MAJOR.MINOR.PATCH)을 준수합니다.
  - **MAJOR**: 기존 버전과 호환되지 않는 큰 변경 및 API 변화가 있을 때 변경
  - **MINOR**: 하위 호환성을 유지하면서 새로운 기능을 추가할 때 변경
  - **PATCH**: 하위 호환성을 유지하면서 버그를 수정할 때 변경
- **문서 버전**: 초안은 v0.1로 시작하며, 최종 승인 시 v1.0을 부여합니다. 이후 수정 시 소수점 첫째 자리를 변경합니다.

### 3.2 커밋 메시지 표준 규격 (Conventional Commits)

형상 관리 리포지토리의 이력을 명확히 추적하기 위해 모든 커밋 메시지는 아래의 형식을 반드시 준수해야 합니다.

`type(scope): message`

- **type**: 변경의 목적을 나타내는 필수 태그 (소문자 작성)
- **scope**: 변경이 발생한 모듈, 컴포넌트, 또는 시스템 영역 (생략 가능)
- **message**: 변경 사항에 대한 명확하고 간결한 설명 (명령조 또는 명사형 권장)

### 3.3 커밋 유형(Type) 필수 태그 정의

| 태그 (Type)    | 의미 (Meaning)                | 설명 및 적용 기준 (Usage & Guidance)                                   | 예시 (Example)                                     |
| :------------- | :---------------------------- | :--------------------------------------------------------------------- | :------------------------------------------------- |
| **`feat`**     | **Feature** (기능 추가)       | 새로운 기능이나 비즈니스 로직을 시스템에 추가할 때 사용                | `feat(auth): 카카오 소셜 로그인 기능 추가`         |
| **`fix`**      | **Bug Fix** (버그 수정)       | 시스템 오류, 크래시, 잘못된 비즈니스 로직을 수정할 때 사용             | `fix(order): 결제 시 포인트 차감 오류 수정`        |
| **`docs`**     | **Documentation** (문서 수정) | 소스코드가 아닌 README, API 명세서, 가이드 등 문서만 수정할 때 사용    | `docs(readme): 설치 및 실행 방법 가이드 업데이트`  |
| **`style`**    | **Style** (스타일 변경)       | 코드 동작에 영향이 없는 포맷팅, 세미콜론 누락, 린트(Lint) 수정 시 사용 | `style(api): 인덴트 스타일 수정 (Tab -> Space)`    |
| **`refactor`** | **Refactoring** (리팩토링)    | 기능 추가나 버그 수정 없이, 코드의 구조나 가독성을 개선할 때 사용      | `refactor(user): 중복 조회 로직 함수화 및 최적화`  |
| **`test`**     | **Test** (테스트 추가/수정)   | 테스트 코드 작성, 리팩토링, 검증 로직을 추가하거나 수정할 때 사용      | `test(payment): 결제 성공 케이스 단위 테스트 추가` |
| **`chore`**    | **Chore** (기타 작업)         | 빌드 스크립트 수정, 패키지 매니저 설정, 단순 자산(Asset) 추가 시 사용  | `chore(deps): lodash 라이브러리 버전 업데이트`     |

### 3.4 추가 권장 태그

- **`perf`**: **Performance** (성능 향상을 유발하는 코드 수정)
- **`ci`**: **Continuous Integration** (CI 설정 파일 및 빌드, 배포 스크립트 수정 시 적용)
- **`revert`**: **Revert** (운영 장애나 결함으로 인해 이전 커밋을 되돌릴 때 적용)

## 4. 브랜치 전략 표준 (Branching Strategy)

프로젝트의 규모, 배포 주기, 인프라 환경에 따라 아래 두 가지 전략 중 하나를 채택하여 전사 표준으로 운영합니다.

### 4.1 Git-Flow 전략 (정기 배포 및 대규모 프로젝트용)

- **main (production)**: 제품으로 출시될 수 있는 가장 안정적인 상태의 최신 브랜치
- **develop**: 다음 출시 버전을 개발하기 위한 타겟 브랜치로, 상시 통합이 일어나는 중심축
- **feature/**: 단위 기능 개발을 위한 브랜치 (develop에서 분기하며 완료 후 develop으로 Merge)
- **release/**: 정기 출시를 위한 최종 QA 및 버그 수정 브랜치 (main과 develop으로 각각 Merge)
- **hotfix/**: 상용(main) 환경에서 발생한 긴급 장애 조치를 위한 브랜치 (완료 후 즉시 배포 및 복사)

### 4.2 GitHub-Flow 전략 (수시 배포 및 지속적 인도용)

- **main**: 상시 배포 가능한 유일한 중심 브랜치로, 엄격하게 보호됨 (Protected Branch)
- **feature-name**: 간결하고 명확한 기능명을 가진 짧은 수명의 개발 브랜치 (main으로 직접 PR 발송)

## 5. 형상 통제 프로세스 (Configuration Control Process)

소스코드의 임의 변경을 제한하고 비즈니스 안정성을 확보하기 위해 다음 4단계 통제 절차를 의무화합니다.

`[1. 변경 요청 (CR)] -> [2. 영향도 분석] -> [3. 코드 리뷰 & 승인] -> [4. 품질 게이트 검증]`

1. **변경 요청 (CR: Change Request)**
   - 개발자는 ITSM 시스템 또는 이슈 트래커(Jira 등)에 변경 사유와 범위를 등록하고 티켓 번호를 발급받습니다.
2. **영향도 분석**
   - 변경 사항이 연관 시스템, 데이터베이스 스키마 및 보안 요건에 미치는 리스크를 검토합니다.
3. **코드 리뷰 및 승인**
   - 형상 관리 도구에서 Pull Request를 생성하고 최소 1인 이상의 지명된 Reviewer 승인을 획득해야 합니다.
4. **품질 게이트(Quality Gate) 검증**
   - 소스코드 병합 전 정적 분석(SonarQube) 결과와 단위 테스트 커버리지 기준(최소 70% 이상 권장)을 충족해야 병합이 허용됩니다.

---

## 6. 지속적 통합 및 배포 (CI/CD) 연계

- **자동 빌드 및 검증 (CI)**
  - 개발 브랜치가 develop 또는 main으로 Merge되거나 Push 이벤트 발생 시, CI 서버(Jenkins, GitHub Actions 등)가 자동으로 빌드 및 테스트를 실행합니다.
- **단계별 환경 배포 (CD)**
  - 빌드 아티팩트(Artifact)는 임의 조작이 불가능하도록 안전하게 격리된 환경(Development -> Staging -> Production) 순서로 검증을 거쳐 순차 배포됩니다.
- **비상 롤백(Rollback) 대책**
  - 배포 실패 또는 상용 장애 발생 시, 형상 관리 도구에 등록된 직전 안정 버전 태그(Tag)를 기반으로 원클릭(One-Click) 자동 복구가 가능하도록 파이프라인을 구성합니다.

---

## 7. 백업 및 보안 정책 (Security & Backup)

- **역할 기반 권한 제어 (RBAC)**
  - 프로젝트 멤버별 업무 범위에 맞춰 Read/Write/Admin 권한을 최소화하여 부여하며, 반기별로 권한 적정성을 검토합니다.
- **민감 정보 노출 금지 (Secret Management)**
  - 데이터베이스 접속 정보, API Key, 패스워드 등 민감한 자격 증명은 소스코드 내에 하드코딩하는 것을 엄격히 금지합니다. (Vault, AWS Secrets Manager 등 전용 도구 연동 필수)
- **리포지토리 백업**
  - 형상 관리 서버의 원격 리포지토리는 유실 방지를 위해 매일 증분(Incremental) 백업을 수행하고, 매주 전체(Full) 백업을 안전한 외부 스토리지에 보관합니다.
